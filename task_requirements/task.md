### 1.2 如何执行本计划

1. 完成第 3 节的项目决策表，填入真实成员、领域、日期和工具版本。
2. 依据第 2 节逐条建立要求与证据对应关系，按第 4 节里程碑执行。
3. 每个成员复制第 5 节模板，形成自己的 story、MVP use case 与验收场景；用课程原版模板校准 use case。
4. 按第 6 至 9 节实现、测试、评审和更新 README，保留可追溯记录。
5. 由未参与相应功能开发的队友执行第 10 节复现流程；完成第 11 节最终核验。

### 5.3 每个 story 的可重复实现流程

1. **选择与确认范围**：选定 story，识别一个或多个必要 use cases，明确哪些属于 MVP；避免未经讨论扩大范围。
2. **规划 UI**：确定新增/修改的 View、按钮、文本框、位置、触发动作和结果显示，更新草图。
3. **定义交互**：按课程模板写 use case，明确每一步用户操作、系统响应以及异常分支。
4. **协调设计**：识别实体、Interactor、边界接口、Controller、Presenter、数据访问和共享 View；与共同使用组件的成员确认契约。
5. **实现与单元测试**：负责人完成自己用例的大部分代码；根据业务行为编写 unit tests，完成 UI 触发和 UI 更新。
6. **本地验证**：运行相关测试，手动走通成功路径、关键异常路径；涉及 API/持久化的用例执行相应集成验证。
7. **提交 PR**：说明 story/use case、行为变化、验证步骤、共享影响和 README/图更新。
8. **代码评审**：队友检查功能、设计、测试和分工；作者处理反馈并重新验证。
9. **集成后验证**：检查共享 View 与既有流程未被破坏；记录实际完成情况。
10. **持续改进**：结合课程内容重构，记录剩余问题和未来扩展。

## 6. 技术设计与可复现约定

本节是 `[计划约定]` 的实现指导；课程硬性边界仍以 R01、R07–R09、R16 为准。目录名、具体接口名和测试框架并非课程指定。

### 6.1 架构责任

| 层/组件 | 责任 | 评审重点 |
|---|---|---|
| Entities | 领域状态和业务规则 | 至少两个领域实体；记录名称、实例变量、相关方法；避免依赖 Swing 或特定 API SDK。 |
| Use Cases | 输入输出边界、应用规则、Interactor、所需数据访问接口 | 用例规则可独立测试；依赖面向业务的抽象，减少与具体 UI/服务的耦合。 |
| Interface Adapters | Controller、Presenter、视图状态转换、外部数据映射 | Controller 接收操作并调用输入边界；Presenter 转换结果供 UI 使用；不把核心业务规则散落到事件处理器。 |
| UI / Infrastructure | Swing Views、API 客户端、文件/数据库实现、入口与装配 | 外部细节实现相应接口；网络与存储失败有明确反馈；入口连接依赖。 |

建议运行链路：

```text
用户操作 Swing View
  -> Controller
  -> Use Case Input Boundary / Interactor
  -> Entity 业务行为 + Data Access Interface（需要时）
  -> API / 文件 / 数据库实现（通过接口接入）
  -> Use Case Output Boundary / Presenter
  -> View 状态更新
  -> 用户看到结果或错误
```

这是执行链路示意，**不是源代码依赖箭头图**。评审时另外检查具体实现是否保持业务层对 UI、API、存储细节的隔离。

### 6.2 SOLID 与设计决策检查

- Single Responsibility：类的责任是否集中，UI、业务规则、持久化是否混杂。
- Open/Closed：加入另一个数据访问实现或显示方式时，是否需要到处修改核心业务代码。
- Liskov Substitution：同一接口的实现是否保持约定的输入、输出和失败行为。
- Interface Segregation：接口是否只暴露调用者真正需要的操作。
- Dependency Inversion：高层用例是否依赖抽象，而不是直接绑定 Swing、API 客户端或数据库类。
- 在适用处使用设计模式，写明解决的问题、选择原因和代价；不为了数量强行加入模式。
- 对暂时偏离理想架构的地方记录原因和后续改善方案，确保最终展示能够解释。

### 6.3 API 验证与记录

1. 根据项目领域选择候选 API，记录名称、官方文档链接和项目用途。
2. 查明实际调用需要的配置、认证、输入、响应及服务限制；这些均由所选 API 决定，材料没有给定。
3. 用项目统一的 Java 环境写最小 PoC；允许调用封装 API 的 Java library。
4. 记录测试日期、环境、运行命令、请求类型、去除敏感信息的响应摘要，以及成功/失败结论。
5. 对 README 中每一个 API 分别标明是否成功调用；更新时区分“PoC 成功”“已集成”“尚未集成”。
6. 定义适配接口，把 API 响应转成应用需要的数据；记录失败、空结果等相关情形的程序反馈。
7. 在程序真实业务流程中验证使用情况，并在展示时如实标明 live API 或测试替身。

建议记录表：

| API | 文档链接 | 项目用途 / 关联 UC | 是否成功调用 | PoC 步骤和证据 | 集成状态 / 当前问题 |
|---|---|---|---|---|---|
| 待选择 | 待填写 | 待填写 | 未尝试 | 待填写 | 待填写 |

API 不必与持久化分别使用两个服务。同一个 API 只要确实展示了外部调用和持久保存/读取，可以同时满足两项要求。若 API 是只读数据源，则另选文件、数据库或可写服务满足持久化。

### 6.4 持久化验证

1. 列明需要保存的业务对象、字段、标识和读取方式。
2. 明确存储位置/服务、文件格式或数据库结构，以及初始数据如何建立。
3. 在 GUI 中创建或修改一条可识别的业务数据，例如带唯一测试标记的记录。
4. 保存成功后退出应用，再次启动或进入新会话。
5. 通过用户可见流程读取，核对关键字段确实保留，不能只验证进程内缓存。
6. 记录测试输入、每一步操作、预期结果、实际结果，以及测试数据清理方式。
7. 对项目相关的读写失败、无记录、格式不合法等场景做适当测试并明确提示。

### 6.5 环境与目录记录

为实现“可复现”，在项目 README/配置中固定真实选择，至少记录：

- 支持的操作系统或已验证系统；JDK 版本；构建工具和版本；测试框架及依赖版本。
- 获取源码、安装依赖、构建、运行测试、启动 GUI 的实际命令；不要只写“用 IDE 打开”。
- 程序入口、必要的工作目录、环境变量名、API 配置方式和首次存储初始化步骤。
- 示例配置和测试数据，不能把真实密钥写进文档或仓库。
- 若使用 UML/sequence diagrams，保留源文件及可重复生成命令；记录所用工具版本。

## 9. 测试与验收设计

`[课程要求]` 迭代开发包含 unit tests；材料没有给出测试框架、覆盖率阈值或强制测试数量。以下为 `[计划约定]`，按实际业务选择相关场景，不为凑数编写无意义测试。

| 验证层次 | 操作 | 通过标准 / 证据 |
|---|---|---|
| 实体与业务单元测试 | 对实际业务规则、状态变化、非法输入写测试 | 符合 use case 与实体规则，输出可复现。 |
| Use case 测试 | 使用可控输入与依赖，验证成功、相关失败和边界路径 | 输出数据、Presenter/输出边界交互、持久化调用符合契约。 |
| Controller / Presenter 边界验证 | 检查用户输入传递、结果与错误状态转换 | UI 不丢失结果，不显示误导状态。 |
| API 集成验证 | 运行真实最小请求及涉及 API 的实际业务流程 | 证明外部 API 被调用；记录环境与结果，和替身测试分开。 |
| 持久化验证 | 保存、退出/重启、读取 | 数据跨会话仍存在，字段正确。 |
| Swing GUI 手动验收 | 按每个 MVP use case 逐步操作 | 能触发用例并正确更新 UI；相关异常有可理解反馈。 |
| 集成回归 | 合并或重构后复测相关共享流程 | 已有功能没有因共享 View、接口或存储变更被破坏。 |
| 独立复现 | 队友用干净工作副本仅依赖 README 操作 | 能配置、构建、测试、运行并重复核心演示。 |

每项验收记录建议采用：

```text
验收 ID：AT-<编号>
对应要求 / Story / Use Case：Rxx / US-xx / UC-xx
被验收版本：<commit hash 或明确版本>
执行人、日期、环境：<实际信息>
初始数据 / 前置条件：<精确记录>
步骤：1... 2... 3...
每步预期结果：<用户可观察行为 / 数据变化>
实际结果与证据：<测试输出、去敏日志或截图>
结论：通过 / 失败 / 未执行
失败项：<issue、负责人、下一步；没有则写无>
```

## 10. 从干净环境复现项目的操作规程

本节定义最终 README 必须能够支持的复现过程。**当前资料不足以写出已经验证可执行的项目命令**；下面的 `<...>` 都是待项目确定后替换的输入，不能直接原样当作运行说明交付。

### 10.1 开发组先准备复现包

1. 确定待验收 commit/version，并确保源码、构建配置、必要测试、图源及说明都已记录在仓库。
2. 写明实际 JDK、构建工具、依赖与已验证操作系统，提供安装/检查方式。
3. 把下面每一项替换为真实且经过验证的操作；若是 IDE 操作，也须写清入口类、运行配置和工作目录。

| 顺序 | README 必须给出的操作 | 必须写清的输入和结果 |
|---|---|---|
| 1 | 获取 `<团队仓库>`，定位 `<验收版本>` | 真实仓库 URL、commit/tag、操作命令。 |
| 2 | 检查 `<JDK/构建工具版本>` | 实际版本检查命令与可接受版本。 |
| 3 | 配置 `<API/存储>` | 配置文件位置、变量名、测试所需权限、测试数据初始化；密钥通过合适渠道单独提供。 |
| 4 | 执行 `<构建命令>` | 从哪个目录执行、预期成功结果和产物。 |
| 5 | 执行 `<测试命令>` | 单元测试与需要网络/服务的集成验证如何区分。 |
| 6 | 执行 `<GUI 启动命令或完整 IDE 操作>` | 启动后应出现的窗口和初始状态。 |
| 7 | 按 `<UC-... 验收步骤>` 操作 | 精确输入、按钮、期望结果和错误提示。 |
| 8 | 完成 `<真实 API 调用验证>` | 能证明调用发生的结果；不得以 mock 冒充。 |
| 9 | 完成 `<持久化重启验证>` | 保存的数据标记、重启方式、重新读取步骤。 |
| 10 | 执行 `<清理/重置步骤>` | 如何恢复测试初始状态、如何区分测试与真实数据。 |

4. 整理每条 MVP 用例的验收脚本与输入数据，不依赖某个开发者电脑上未说明的本地状态。
5. 若有生成的设计图，说明怎样从源文件重新生成并检查与当前版本一致。

### 10.2 独立执行者进行复现

1. 使用独立工作副本与干净测试数据，不复用开发者未文档化的配置。
2. 只按 README 执行第 10.1 节流程，逐项记录环境、命令、输入与输出。
3. 检查全体成员的 stories/MVP 用例是否都有可重复演示路径。
4. 检查成功路径之外，项目实际相关的非法输入、无数据、API 失败或读写失败是否给出明确反馈。
5. 记录需要口头补充的地方，提交文档或实现修复；修复后复测受影响步骤。
6. 只有当全部必需步骤通过，才将复现状态记为“通过”；依赖外部服务导致无法执行时明确记录“未执行/受阻”，不能记作成功。

### 10.3 API 暂时不可用时的演示安排

课程允许设计良好的 MVP 在 API 尚未完全集成时仍能展示主要流程。可以保留单独标记的测试替身/固定数据来演示界面与用例，但应：

- 清楚区分真实服务模式和演示数据模式，不混淆调用状态。
- 保留真实 API PoC 的证据、当前集成进度、失败原因与后续动作。
- 在 README 和展示中如实说明限制。
- 对 R08 的最终达标不作自行豁免；若存在疑问，尽早询问课程团队。

## 11. 最终核验与展示计划

### 11.1 必须满足或确认的核验项

- [ ] 已选领域、团队/项目名，并完成共同制定 stories 和初始 UI 的过程。（R03、R10–R13）
- [ ] Java + Swing GUI 可运行；若改用 JavaFX，已有明确批准；没有用 Web app 替代。（R01）
- [ ] 每个成员都完成至少一个完整 user story，规模与成员数量相称。（R04）
- [ ] 每个成员主导至少一个 MVP use case，并编写其主要组件和 UI 相关代码。（R05–R06）
- [ ] README 明确 use case 负责人，共享组件有协调，各成员都有实质代码贡献。（R05–R06、R22）
- [ ] 至少两个实体，名称、实例变量和相关方法清楚。（R16）
- [ ] 按课程模板记录 use cases，区分 MVP 与后续功能。（R14–R15）
- [ ] 外部 API 确实使用；每个列出的 API 有文档、用途和真实调用状态。（R08、R17）
- [ ] 可以展示持久保存并在新会话读取数据。（R09）
- [ ] 有遵循 Clean Architecture / SOLID 的设计尝试、重构过程和可解释的取舍。（R07）
- [ ] 开发全过程有 PR 和代码评审；相关功能包含适当 unit tests。（R02、R18）
- [ ] README 与实现同步，包含所有必需信息；模板不涵盖的 API 调用状态也已补齐。（R12–R17）
- [ ] 已核对所有真实日期与 Reading Week 后第二次 lab 的设计安排。（R11、R19、R24）
- [ ] 全员每周参与，缺席/延迟已沟通；遵守团队合作与职业素养要求。（R21–R23）
- [ ] 学期结束前完成项目，准备好主要交付物——小组展示。（R19–R20）

### 11.2 本计划为可复现增加的完成标准

- [ ] README 的所有运行占位已换为经过验证的真实信息。
- [ ] 干净环境构建、测试、GUI 启动、核心业务、API 与持久化复现有记录。
- [ ] 需求 → story → use case → 成员 → 代码/PR → 验收证据可以相互追踪。
- [ ] 图表与实现一致；采用图生成工具时保留源文件与生成方法。
- [ ] 已知问题、未完成内容、未来扩展均如实标注。
- [ ] 没有将候选 API、mock、未运行的测试或未完成任务宣称为已通过。

### 11.3 最终展示脚本的内容顺序

以下顺序为建议，不预设课程要求的时长、幻灯片数量或分工方式。

1. **项目与用户价值**：团队、领域、目标用户、核心 stories 与 MVP 范围。
2. **功能演示**：展示主要 GUI 流程，覆盖各成员负责的完整功能；演示真实 API 用途和持久化效果。
3. **设计说明**：实体、分层、用例链路、接口边界；解释如何尝试遵循 Clean Architecture 与 SOLID，如何在适当处使用模式。
4. **设计取舍与演进**：为什么这样设计，评审后如何修改，哪些重构改善了代码或协作。
5. **团队开发实践**：展示 PR、review、unit tests、git 历史和公平分工的证据；每人能解释自己的实现。
6. **局限与后续改进**：公开当前不足、open issues、未来功能和可能的设计改进。

正式展示时长、格式、提交平台和其他评分条目需要以课程另行发布内容为准。
